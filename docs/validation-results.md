## macOS 观察与动作耗时（2026-09-28）

在正在运行的宿主上，用当前源码的 `CuaBackend` 直接连接驱动，对同一个 Safari 窗口计时。测量时打包后的 CLI 尚未包含这次改动；重新打包后的端到端计时见下一节。

改动前，`observe` 约 8.1 秒：`listApps` 约 1.7 秒，加上两次带辅助功能树的 `getWindowState`（约 5.1 秒返回无图像，紧接着约 1.3 秒才带截图）。一次滚动约 8.5–9.7 秒：`listApps` 约 1.7 秒、`listWindows` 约 0.07 秒、坐标预热抓取约 4.2 秒、滚动本身约 2.4–3.8 秒。

改动后：

| 路径 | 耗时 | 构成 |
|---|---|---|
| `observe`（距上次 `listApps` 已超过 1 秒） | 8.2 秒 | `listApps` 1.7 秒 + 空帧 5.0 秒 + 有效帧 1.5 秒 |
| `observe`（1 秒内刚列过应用） | 6.5 秒 | 空帧 5.1 秒 + 有效帧 1.4 秒 |
| 观察后 1 秒内滚动 | 3.2 秒、4.3 秒 | `listWindows` 约 0.09 秒 + 滚动 3.1–4.2 秒，不再预热、不再枚举应用 |
| 截图预热过期后滚动 | 9.8 秒 | `listApps` 1.7 秒 + 预热 4.2 秒 + 滚动 3.8 秒 |

观察做不到 5 秒以内：驱动合并请求树和截图时，先固定花约 5 秒返回一帧没有图像的结果，下一次才带上截图，两次合计约 6.5 秒。中途取消第一次会使后面的抓取一直为空。先单独要截图也会先失败约 4.2 秒（`No content produced`），并不能比现有重试更快。

紧跟观察的坐标动作可以到 5 秒以内。预热大约只保持 1 秒；这 1 秒里再做一次 `listApps`（约 1.7 秒）就会错过它。因此应用列表缓存 1 秒，并在有效截图结束时重新计时。超过这个窗口后仍要预热：不做预热时，滚动在约 4.1 秒后以 `px_capture_unavailable` 失败。

## macOS 应用枚举提速（2026-10-13）
归属校验原来调用驱动的 `list_apps`。它还要扫描全部已安装应用（本机 215 个），每次 2.1–3.6 秒，而 `session_open`、每次 `observe` 和每个动作前的校验都要做一次。现在 macOS 改用 `get_accessibility_tree` 取运行中的应用，约 20–50 毫秒；工具报错、返回结构不符或传输异常时回到 `list_apps`，只是更慢。Windows 不变。授权判断本身没有改：仍要求 pid 与 Bundle ID 同时匹配。

等价性（驱动 0.28.2，本机）：`list_apps` 的运行中应用与 `get_accessibility_tree` 的应用列表各 21 个，pid 与 Bundle ID 完全一致。把一次性 Fixture 的第二个实例用 `NSRunningApplication.hide()` 隐藏后（窗口 `isOnScreen` 变为 false），两边仍都列出它。

计时方法：工作区编译出的 `Runtime` 与 `CuaBackend` 经运行中 App 的驱动套接字，只操作一次性 Fixture；临时数据目录和临时凭据，由测试代码批准本轮测试客户端；每次调用前停 3 秒模拟模型间隔（运行时对应用列表只缓存 1 秒）。用户的宿主、已有配对和其他窗口没有被操作。

| 步骤 | 改动前 | 改动后 |
|---|---|---|
| `targets` | 2.2 秒 | 0.13 秒 |
| `session_open` | 2.2 秒 | 0.07 秒 |
| `observe`（树加截图） | 2.9–3.0 秒 | 0.96–0.97 秒 |
| `act` 输入加附带观察 | 8.3 秒 | 3.9 秒 |
| `act` 点击加附带观察 | 9.7 秒 | 4.0 秒 |

改动前 `act` 加附带观察的 8.3 秒中，两次 `list_apps` 占 4.7 秒；改动后剩下的大头是驱动自己的动作耗时（`type_text` 约 2.6 秒、`click` 约 2.8 秒）。Fixture 点击和输入后由独立文件确认效果无误。

授权全部应用时，`targets` 也改为一次取全部窗口再按应用分组（macOS）：原来对每个应用各调一次 `list_windows`，每次约 45 毫秒。本机 20 个应用、144 个窗口，从 0.93–1.07 秒降到 0.13 秒，结果逐项相同。显式应用清单仍逐个应用枚举，不去读清单之外的窗口。

没有改变也没有证明的部分：Safari 上记录过的“先空等约 5 秒再给截图”只出现在 Safari，对 Fixture 静置 12、40、100 秒后首次合并取树和截图仍只要 1.1–1.7 秒，所以这条结论不能推广到所有窗口。

## 只取元素的观察（2026-10-13）
`observe`、`wait` 和 `act` 的 `observe` 新增 `elementsOnly: true`：不抓取截图，快照只用于元素点击、输入和按键。没有截图的快照不带 `imageWidth` / `imageHeight`，元素没有 `bounds`；坐标点击、拖拽和滚动在派发前被运行时拒绝（`invalid_request`）。它不能与 `screenshot: true` 或 `elements: false` 同用，冲突在动作派发前就报错。`act` 的 `verify` 在没有附带观察、或附带的观察是 `elementsOnly` 时，轮询也不再抓截图；带截图的附带观察仍复用满足条件的那次观察，不多抓一次。原有 `screenshot: false` 的含义不变：只省略返回内容，快照仍可用于坐标。

驱动事实（0.28.2，本机，一次性 Fixture）：`get_window_state` 带 `include_screenshot: false` 时不返回图像，也不返回窗口几何（`windowBounds` 为空），因此运行时另用 `list_windows`（约 30–60 毫秒）取窗口边界，先于取树，窗口在两者之间移动时动作前的校验会判为过期。同一界面状态下，仅树与树加截图返回的 76 个元素逐项一致（角色、层级、标签、值、状态、位置、可用动作），都带元素 token，`elementsComplete` 同为 false。

计时方法同上一节（每次调用前停 3 秒；用于对比的“改动前”数字见上一节）：

| 步骤 | 树加截图 | `elementsOnly` |
|---|---|---|
| `observe` | 0.93–1.12 秒 | 0.30 秒（树 0.20–0.24 秒） |
| `wait`（条件已满足） | 1.10 秒 | 0.28 秒 |
| `act` 输入加附带观察 | 3.9 秒 | 3.0 秒 |
| `act` 点击加附带观察 | 4.0 秒 | 3.2 秒 |

`verify` 轮询：无附带观察时轮询用只取树的 `getWindowState`（0.36 秒）；附带 `elementsOnly` 同样只取树；附带完整观察时轮询带截图（1.07 秒），并直接发布那次观察。三种情况动作后的状态都是 `verified`。在只取元素的快照上点击带 `elementId` 的文本框：该文本框不支持 AXPress，macOS 上要用元素位置，记录为 `failed` / `invalid_request`，没有任何点击发出；`type` 带 `elementId` 输入同一文本框则成功。

Fixture 的窗口很小，取树和取图都很快，节省来自去掉抓取本身。Safari 上记录过合并请求先空等约 5 秒，对 Fixture 静置 100 秒内都没有复现，所以那种窗口上能省多少不在本节实测范围内。

未覆盖：Windows 驱动源码里 `include_screenshot: false` 语义相同，但 Windows 上只有单元测试，没有在虚拟机里实际运行；浏览器后端的只取元素路径仅由单元测试和 Chromium 集成测试覆盖。

## 设置值与菜单动作（2026-10-13）
新增两个后台可用的动作：`setValue` 用 `elementId` 整体替换元素的值，`menu` 用菜单名路径调用应用菜单项。两者都走驱动的辅助功能接口（`set_value`、`invoke_menu`），没有投递方式参数，不移动焦点。Fixture 新增了弹出按钮、滑块和带嵌套项、禁用项的 “Fixture” 菜单，状态写入同一个证据文件（`choice`、`level`、`count`），作为独立证据。

计时和方法同上两节：工作区编译出的 `Runtime` 与 `CuaBackend` 经运行中 App 的驱动套接字，只操作一次性 Fixture，临时数据目录和凭据；每个结果都与证据文件对照。另在直接调用驱动的实验里，每次菜单调用后用 `lsappinfo` 检查前台应用：始终是用户正在用的应用，没有变化。

| 动作 | 结果 | 独立证据 |
|---|---|---|
| `menu` Fixture › Record | `executed` / `unconfirmed`，0.7 秒 | `count` 4 → 5 |
| `menu` Fixture › More › Record Twice | 同上，0.95 秒 | `count` 5 → 7 |
| `menu` 路径不存在 | `failed` / `not_found`，驱动拒绝码 `menu_path_unavailable` | `count` 不变；随后的动作照常执行，运行时没有停机 |
| `menu` 被禁用的菜单项 | 同上 | `count` 不变 |
| `menu` Apple 菜单（含前后空白、大小写不同的写法） | `failed` / `permission_denied`，派发前被拒绝（0.1–0.3 秒，驱动只收到归属和窗口校验，没有 `invoke_menu`） | 无变化 |
| `setValue` 滑块 `6` | `executed` / `unconfirmed`（驱动读不回），2.7 秒 | `level` 0 → 6 |
| `setValue` 文本框 | `verified` / `confirmed`（驱动读回），`verify` 条件按整个值满足 | 再设一次得到的是新值，不是追加；随后经菜单 Record 写入的 `text` 是 `第二次` |
| `setValue` 弹出按钮 | `failed` / `invalid_request`，派发前被拒绝（同样没有 `set_value` 调用） | 无变化 |

驱动事实（0.28.2）：`invoke_menu` 对缺失、重名、禁用的路径返回 `isError`、错误码 `menu_path_unavailable` 和结构化的 `status: "refused"`，没有 `action` 元数据；成功时结构化结果的 `effect` 是 `unverifiable`。路径各段只忽略首尾空白，区分大小写；只给一个顶层菜单名也返回成功，但没有产生命令（计数不变）。`set_value` 对原生 `NSPopUpButton` 返回 `AXPopUpButton … has no AX children … no fallback available`，`isError` 为真但没有错误码；运行时把没有错误码的失败按“结果不确定”处理并停机，所以弹出按钮在派发前就被拒绝，而不是等驱动报错。对不可写的按钮，`set_value` 同样报“已发出（未确认）”而不报错，因此“已发出”不等于生效，要读回核对；直接调用驱动给滑块写 `99` 时，控件把值夹到上限 10。

Apple 菜单保护依据快照里的原始菜单栏：第一个菜单栏项就是系统 Apple 菜单（观察本来就不列它），路径第一段与它的标签相同就拒绝；快照里没有菜单栏时也拒绝，因为无法识别它。

未覆盖：Safari 网页 `<select>` 上的 `set_value`（驱动说明里有专门的弹出按钮模式，错误信息提到针对 Safari 的回退）未测，也没有放开；Windows 的 `set_value` 与 `invoke_menu` 只有单元测试，没有在虚拟机里运行；浏览器后端的 `setValue` 由 Chromium 集成测试覆盖。

## 网页输入框与终端类应用的输入（2026-10-16）
起因是 2026-10-15 在 OrcaTerm（Tauri 应用，内嵌 xterm.js）中实际使用时，`type` 两次以 `unknown` / `type_text_incomplete` 结束并停机，而命令实际已完整输入。为核实原因，做了一个一次性 WKWebView 夹具：页面上一个文本框在每次输入后立即清空，模拟终端把字符交给 shell 后清掉辅助输入框；另一个近似 xterm.js 的按键处理。页面把收到的字符写入独立文件。经运行中 App 的驱动套接字直接调用 `type_text`（后台，带元素 token），当时系统输入源是微信输入法拼音。没有操作用户的窗口和剪贴板。

| 文本长度 | 驱动耗时 | 驱动结果 | 页面实际收到 |
|---|---|---|---|
| 20（两种文本框，两轮） | 4.1–5.5 秒 | `type_text_incomplete`，“delivered 0 of 20”，结构化结果 `retryable: true`、`retry_from_character: 0` | 全部 20 个字符，各一次，大小写完整 |
| 150 | 10.2 秒 | 同上，“0 of 150” | 150 个字符 |
| 600 | 28.4 秒 | 同上，“0 of 600” | 600 个字符 |

结论：
- 驱动按辅助功能读回来计算“已送达”，对会自行清空的网页输入框没有意义；按它的提示重试会把整段文本再输一遍。运行时没有转述这个提示，但把结果记为 `unknown` 并停机。
- 后台逐键输入约为 4 秒固定开销加每字符 40 毫秒。默认 `timeoutMs`（15 秒，加 5 秒宽限）约能输入 400 字符，最大 30 秒约 750 字符。按实际使用记录里前台约每秒 9 个字符估算，前台上限约 300 字符；记录中那次 600 字符的前台输入以运行时的 “Active action interrupted” 结束，与超出时限相符（宿主和运行时都不监测鼠标）。
- 拼音输入法开启时，后台路径的字符全部原样到达，与实际使用记录的复盘一致。

Skill 据此补充了终端类应用的做法（单键用 `key`，命令走剪贴板粘贴，回车前核对整行，结束标记与分段等待）、长文本与快照时效的限制、前台控制尽快交还，以及输入法说明。

未覆盖：前台输入的速度与输入法影响；窗口被完全遮住时网页视图是否停止重绘（后台启动的夹具窗口落在当前应用之前、系统报告可见，没有为测试移动用户的窗口）；后台 `cmd+v` 能否在 WKWebView 应用中粘贴。驱动二进制中还有派发前的拒绝码 `type_text_synthesis_budget_exceeded`，本次 600 字符没有触发。

| 遮挡 | 盖上后观察带 `covered: true` 和 `screenshotMayBeStale: true`，文字等待超时时说明截图可能没有更新；移开后两个字段消失。后台启动的夹具落在用户窗口之后时也报告为被遮挡，但当时截图仍在更新（识别读到了新输入），所以这只是提示 |
| 用户输入空闲时间 | 读 HIDIdleTime 得到 1168 毫秒（用户正在使用电脑），前台动作此时会以 `busy` 拒绝 |
| `request_all_apps` | 运行时发出 `grant_request`（名称、现有应用范围、短标识），收到 `grant_all_apps` 后返回已授权；`capabilities.client.shortId` 与之一致 |

另外两点影响实现：未激活的 WebKit 应用，第一次观察只有窗口外框，网页部分第二次观察才出现在辅助功能树里；它的 Edit 菜单在树里只列出系统附加的“自动填充”“表情与符号”，剪切、拷贝、粘贴不在其中。因此后台粘贴在快照里找不到“粘贴”项时，按“编辑”菜单的语言尝试该语言的名称，路径不存在时驱动在按下任何菜单项之前返回 `menu_path_unavailable`。

两处驱动行为已报告上游：自行清空的网页输入框被误报为未送达并建议整段重试（[trycua/cua#5354](https://github.com/trycua/cua/issues/5354)；上游 `main` 的辅助功能写入路径已把网页里的“值没变”视为无法确认，逐键路径还没有），以及后台 ⌘V 到达不了未激活的 WKWebView 应用、驱动却回报成功（[trycua/cua#5355](https://github.com/trycua/cua/issues/5355)）。

Windows 11 ARM64 虚拟机：托盘程序与界面测试程序构建无警告；界面测试全部通过，包括 Agent 发起的授权弹窗（短标识、现有范围、默认拒绝、批准发送带请求标识的 `grant_all_apps`、过期撤回）、客户端页的标识列，以及用内存替身验证的剪贴板会话协议和两遍识别的合并。`--input-idle` 返回空闲毫秒数。`--recognize-text` 识别同一张示例图：虚拟机只装有中文识别器，`ls -la` 被认成 `IS —la`，半角标点变成全角，运行时比较文字条件时会统一全角与横线，但认错的字母无法补救。Parallels 与 Mac 共享剪贴板，所以没有在虚拟机里操作真实剪贴板。

未覆盖：新的 macOS 宿主弹窗与 `host_features` 没有在打包后的 App 中运行（不能在不停止用户 App 的情况下替换它）；签名 App 读取剪贴板时系统是否弹出隐私询问（测试用的辅助进程继承了终端的“始终允许”）；前台分段输入在用户实际操作下的表现（会占用用户的键盘）；驱动自身的 `type_text_synthesis_budget_exceeded`（运行时的估算先拒绝了）；Windows 上的粘贴端到端效果。
