# Architecture decisions

## One execution owner

The Swift AppKit host owns system permissions and directly spawns Cua Driver in embedded mode. A dedicated parent-liveness pipe ensures host death closes the daemon. The host also launches the Node runtime; it connects to the driver through the native SDK's private socket interface. No MCP server is needed for CLI actions.

The desktop adapter replaces its SDK client before the driver's five-minute implicit idle-session limit and reconnects once after a read-only transport failure. It never replays a dispatched input action after uncertainty.

Only the host's stdin pipe can approve pairing, expand an existing client's desktop scope and change listeners. A pairing approval persists a grant that includes foreground control; sessions do not prompt again, and revocation removes the whole grant. Agent-facing RPC has no control-plane method or raw-driver escape hatch. Native launch configuration disables Cua telemetry/update checks and removes inherited Node/DYLD/Cua overrides. Local configuration does not provide a sandbox against the same OS user.

New pairings without an application list or browser-only request default to `allApps: true`. The persisted flag grants all current and future desktop applications and windows, while isolated-browser access remains a separate permission. Explicit application lists remain an advanced restricted mode; `--browser` alone remains browser-only. Existing stored grants without `allApps` retain their original scope, so an App update cannot silently widen authorization. The App's Clients → Allow all apps control explicitly confirms a host-only `grant_all_apps` command for an existing desktop client; browser-only clients are ineligible. It sets `allApps: true`, clears `appIds` and includes foreground permission while preserving client identity, credential and browser permission. Persistence must succeed before the expanded grant becomes usable or the host reports success; a concurrent revocation must not be undone by a late upgrade. Neither CLI nor MCP exposes this control. Host approval and client lists display the all-application scope explicitly; a `pair_allow` decision must acknowledge `allApps: true` for that scope, so an older host that cannot display it cannot approve it. This grant does not replace OS permissions or broaden backend capabilities. Sessions remain in `background` mode by default; foreground must be requested explicitly. Pause and emergency stop are independent of grant scope.

Authenticated `capabilities` and `doctor` responses include a normalized `authorization` for the calling client. `preflight.profile.authorization` copies only a valid online response; it remains absent for offline credentials, older hosts or malformed optional metadata. It is never inferred from a credential file or a target list. Desktop targets outside the grant remain filtered before session creation. The operating guide carries the user's task authorization across application, window and session changes. Foreground control within that task requires a short notice, not a repeated approval; competing user input still requires coordination, and the guide cannot widen runtime grants.

## Packaged on-demand host startup

Starting in v0.6.1, `src/runtime-client.ts` defers runtime access until an actual RPC. stdio MCP initialization and tool listing need no host. On Windows with the default pipe, the client probes discovery without sending an RPC. If unavailable, it validates the same complete package's CLI, Node, host and build receipt before invoking `ComputerUse.WindowsHost.exe --ensure-running`. Starting in v0.7.0, macOS uses the same lazy flow with a verified `.app`, its native `--ensure-running` helper, a private socket and exact-path LaunchServices background launch. Source execution and a custom `--socket` never auto-start a host; HTTP and SSH setup remain separate. The client sends the original RPC once after readiness and never retries a dispatched action to repair startup or transport failure.

The native helper serializes concurrent startup requests and waits up to 35 seconds. It emits one JSON result, requiring both live host identity (PID, process start time, executable and OS user/session) and a successful probe of the current-user IPC endpoint before returning `ready`. The long-lived background host does not inherit the MCP stdout stream. The helper requires an interactive user session and cannot override Windows signing or execution policy.

The Windows pipe accept loop reserves one of its 64 instances for the next listener, creating and arming it before handling or disposing the previous connection. An early client disconnect reported as `ERROR_NO_DATA` replaces that instance without dropping the pipe name; other listener failures remain fatal. At most 63 requests are handled concurrently, with a 10-second deadline for clients that connect without sending a request. A separate Windows transport regression executable exercises real pipe connections without accessing desktop content or user credentials.

The host persists lifecycle metadata in private `host-state.json`, separately from credentials and ordinary preferences. On Windows, native state/discovery access uses a per-user, per-path named mutex across sessions, with a two-second lock deadline, so readers cannot enter the intermediate steps of file replacement. The helper validates the directory without rewriting its ACL; the host remains responsible for creating and securing its private data. Pause and emergency stop continue to block automatic and sign-in startup across host exit. Only the local Resume/Restart Services buttons clear a pause or emergency stop. Reopening, login and update launches preserve the block; merely opening an instance shows Settings. Runtime `ready` events cannot clear a later pause or stop, and full host readiness is published only after the IPC listener and, on Windows, discovery are ready. See [validation results](validation-results.md) for tested coverage of this path.

The explicit, Agent-independent CLI `recover --profile NAME` uses the verified same-package Host `--recover-fault` helper. This path does not call the UI restart method that clears user blocks. It only restores failed service workers after their predecessors exit, is serialized and rate-limited, and treats concurrent user stop/pause as authoritative. A healthy host is unchanged. Known unauthorized credentials are refused before recovery when IPC is available; an offline service cannot authenticate, so the original credential is always authenticated again after recovery before success is reported. Recovery grants no access and never modifies clients or action records. It accepts no action to replay. Sessions/snapshots from a restarted runtime are invalid; persistent unknown request records remain queryable, and a new session plus fresh observation is required before continuing. Released v0.7.0 packages lack this command and retain their local recovery fallback.

## App and standalone Skill onboarding

v0.7.0 shares one generated, standalone `skills/computer-use/SKILL.md` between App and Agent entry points. Its maintained inputs contain stable operating rules and embedded macOS/PowerShell discovery/install scripts; packaging rejects missing or stale generated content. App Connect primarily copies a short setup prompt. The receiving Agent retrieves the complete Skill through the bundled CLI and uses its own installation mechanism; the App has no Agent-specific installer. The initially collapsed Advanced connection controls use one profile (default `default`) for prompt/Skill hints, pairing commands and MCP configuration. Path hints are data and contain no credentials. CLI file export refuses existing files.

`skill prompt`, `skill export`, `instructions` and `preflight` are local commands before the authentication gate. They never start a host. Preflight lists only profile names, reports offline credentials as unverified and checks only the selected credential through read-only capabilities against an already-running runtime. First installation uses the official stable release, native OS architecture, existing metadata/checksum rules and macOS signature/notarization checks, without Git/global Node. The complete Skill includes a v0.6.1 fallback rather than treating missing new commands as a missing installation. First OS permissions and pairing remain local user approvals.

## Stable interface, replaceable adapters

`src/contracts.ts` defines backend observations and execution operations. `src/schema.ts` is the shared validation and tool-schema source. `src/runtime.ts` performs authorization, session ownership, leases, stale-snapshot rejection, deduplication and result recording. Cua 0.28.2 and Playwright 1.63.0 are behind independent adapters.

Capabilities describe the implemented subset. The Cua driver supports straight drags and line/page scrolling, so the public interface exposes those units instead of pretending it supports arbitrary paths or pixel-precise scrolling. Driver `action.effect` uncertainty is not converted into success.

## Observations

Adapters return backend element references, geometry and, where the platform exposes them, values and enabled/selected/range state. Password values are dropped inside the adapters: the Cua adapter discards values of secure or password roles and mask-only values (macOS reports a secure field as `AXTextField` whose value is U+F79A placeholders of the same length), and the browser adapter does not read password inputs. Dropped values never reach results or conditions. Windows UI Automation does not expose password text, but WinForms returns a localized access-denied placeholder that is passed through because the driver does not report the password flag. The desktop drivers omit empty values, so an empty field has no `value`.

The runtime assigns public element IDs and maps them back to backend references per snapshot, so driver tokens stay internal. Within a session an element keeps its ID while its role, label, tree depth and rounded bounds are unchanged; a new label or position produces a new ID, so a remembered ID cannot silently address different content. Results truncate values after 2,000 UTF-16 units and report `valueLength`; conditions compare the full value.

`observe` can omit the screenshot or the element list without changing snapshot rules. `elementsOnly` is different: it skips the capture itself, so the snapshot has no pixel geometry or element bounds and the runtime rejects coordinate actions on it before dispatch. Verification polls skip the capture whenever no screenshot-bearing observation will be attached. `since` returns only added or changed elements plus removed IDs, and only when it names the session's latest published element list; otherwise, or when no element carried over, the list is complete. `act` can attach the next observation. It is taken in the action's queue slot, reuses the observation that satisfied `verify`, is omitted after an `unknown` outcome, and is skipped with `observationError` when less than one second of the 60-second response budget remains. Observation failures never change the action record.

## Lifecycle and outcomes

The runtime keeps a private metadata-only action journal. An ID with different arguments is rejected; a repeated identical ID returns its known state. The `observe` option shapes only the response and is not part of an action's arguments. `queued` or `running` records found at restart become `unknown`, never replayed. Persisting action state must succeed before input dispatch; failures stop execution.

An action consumes its snapshot before being queued. Cancellation and authorization are checked again after async validation and journal writes. Both adapters report the moment input is dispatched; a timeout or cancellation before that point fails or cancels the action without sending input and does not stop the runtime. Aborting dispatched input cannot stop it, so when `timeoutMs` expires after dispatch the runtime waits up to 5 more seconds for the driver call to finish before treating the outcome as unknown. Interruption or transport uncertainty after desktop dispatch stops the runtime because aborting a client future cannot prove a native drag has stopped. The controlled browser declares its input contained: an interrupted browser action closes its page, and an uncertain browser outcome is recorded as `unknown` without stopping desktop work. Completed dispatch with an unconfirmed effect is `executed` with `effect: "unconfirmed"`, never `unknown`: delivery is certain, only its effect is unproven. It can be checked by a supplied read-only condition and does not require terminating a healthy driver. Journals written before this distinction are migrated on load by matching the former message exactly. The host terminates interrupted input as the final boundary; held-input cleanup still requires desktop validation.

`executed` is distinct from `verified`. Explicit element/title checks can verify an observable condition; they are not a substitute for inspecting saved project files, exported media or creative quality. Incomplete element trees cannot verify absence. Read-only waits honor their deadline, retry only stale observations and return the exact observation that satisfied the condition.

## Browser and data

The browser is a new headless Chromium context with a fixed CSS viewport and no normal user profile. Authorization covers the shared controlled-browser space, not a website allowlist. The adapter returns semantic elements from the main document and a screenshot, validates DOM/geometry state, dismisses JavaScript dialogs and stores downloads in unique directories. Existing user browser sessions, file URLs and arbitrary JavaScript execution are not exposed.

IPC and CLI image files are private to the current OS user. MCP returns images as image content rather than duplicating base64 into text. Default journals exclude screenshot contents, text, URLs and window titles. Diagnostic output contains fixed messages and status metadata.

## Packaging

The App includes a fixed Node runtime, a fixed embedded driver and production dependencies. It does not require globally installed Node/Rust. Debug builds use ad-hoc signing; Developer ID signing, notarization and a clean-user test are separate release gates. HTTP is disabled on each App launch and binds only loopback when explicitly enabled.

v0.6.1 packages a warm-white and dark-charcoal cursor icon for macOS App and Windows EXE, tray, windows and installer, plus a white cursor body for the macOS menu bar. These are display resources, not a signing or authorization mechanism. Windows packages remain unsigned and subject to SmartScreen / Smart App Control reputation and system policy; macOS Developer ID does not apply to Windows.

## Host settings and updates

Both hosts present the same six settings pages; the menu bar and tray menus keep only quick actions (status, settings, pause/resume, emergency stop, restart, update notice, check for updates, quit). Interface text lives in per-host tables (`HostCore/Localization.swift`, `L10n.cs`) chosen from the system language, with tests requiring identical keys and placeholders. The runtime's `clients` event carries each grant's `allApps`, app IDs and browser/foreground flags for display only; tokens never leave the runtime. Hosts treat a missing `allApps` field as a scoped grant for compatibility. Scope-change results use an optional, request-correlated `operation` field on the existing `clients` event, without introducing a new event type. Both hosts wait for this result before reporting an upgrade as saved. Failures and stale results do not clear pause or emergency stop. The existing event type preserves compatibility with Windows hosts that reject unknown events.

Update logic exists once, in `src/update.ts`, and both hosts run it through the bundled Node (`runtime/cli.js update check|download`), so it works without pairing or a running runtime. It reads `repos/starroyhq/computer-use/releases/latest`; when the unauthenticated API answers 403, 429 or 5xx or cannot be reached, it follows the `github.com/starroyhq/computer-use/releases/latest` redirect (which skips drafts and prereleases) and reads that release's metadata asset and tagged notes file instead, so a shared IP that used up the hourly quota gets the same answer. It offers a release only when its tag is a plain `vMAJOR.MINOR.PATCH` newer than the running version; drafts, prereleases and downgrades are never offered. Every request and redirect is re-checked against HTTPS `api.github.com`, `github.com` and `*.githubusercontent.com`, and response sizes and times are bounded. A download must match the user-confirmed version, the release's `.sha256` file, the per-platform `.json` metadata (version, platform, 40-hex commit, `sourceDirty: false`, archive name, size, digest, signing mode) and GitHub's asset digest when present; it is written to a private partial file and renamed only after the hash matches.

On macOS a package is installed only when the running app is Developer ID signed. The host extracts it with `ditto`, requires exactly one `Computer Use.app` with the same bundle identifier and a newer version, validates the whole bundle (nested code, strict mode) against a requirement pinned to the running app's own Team ID, and requires `spctl` acceptance. After the user confirms, a detached script waits for the host to exit, moves the old bundle aside, puts the new one at the same path (so absolute paths in agent configuration and the CLI symlink stay valid), restores the old bundle if that fails, and reopens the app. Because the bundle identifier and designated requirement are unchanged, TCC grants are expected to carry over. Translocated or unwritable installations fall back to revealing the verified bundle.

Windows portable copies download and verify the ZIP, then reveal it so the user can quit the tray host and replace the folder manually. Installer-based updates have been available since v0.6.0: when the current user's uninstall registration points to the running host's directory, the host downloads a verified installer with `--installer` and offers Run Installer. The user completes the setup wizard, which uses `--quit` to stop the tray host and its service before replacing files. Upgrades preserve the install location, paired clients and settings. Windows packages remain unsigned; releases through v0.5.0 provide portable ZIPs only.

ZIP packages, a macOS DMG and Windows setup installers have been available since v0.6.0 and remain the v0.7.0 delivery formats. Release CI verifies notarization and stapling of the macOS App and DMG; this release's result remains to be confirmed. Windows 10, native x64 desktop acceptance and the complete Windows upgrade flow from downloading a real release to running its installer still need validation.
